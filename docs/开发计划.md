# BearPassword 本地版开发任务拆分 v3

- **对应需求**：《BearPassword 本地版二次开发需求文档 v3 定稿》（纯本地、无云同步、通用验证器 TOTP；v3 已关闭全部待确认项）
- **v2 → v3 同步调整**：删除旧迁移任务 T33 / T34 与扩展裁剪任务 T41；T02 / T03 增加 `bear-password-index` 删除；扩展锁定保留（仅 T40）；恢复密钥按 128 位原账户密钥格式执行；生物识别保留为快捷解锁
- **基线**：https://github.com/isxuewei/BearPassword.git，桌面端 26.9.9，Electron + Vue 3 + TypeScript
- **工作量标注说明**：S ≤ 1 天、M = 2–4 天、L = 5 天以上，均为粗估、非承诺；实际以开发中核查代码后的评估为准。任务按依赖顺序排列，同一阶段内无依赖的任务可并行。
- **开发铁律**：每阶段结束必须跑通 `npm run typecheck`；不顺手重排生成文件、截图与锁文件（原仓库 AGENTS.md 约定）；涉及保险库加密、令牌、剪贴板、本机桥接的改动必须在提交信息中说明安全影响。

## 风险与注意事项

1. **最大风险在 T22–T23**：登录态是贯穿路由、启动、自动锁定、扩展桥接的横切逻辑，删除不彻底最容易留下“登录页闪现”或“未解锁进主界面”的缺口；这两个任务必须先做、单独验收，不宜与其他任务混在一个提交里。
2. **令牌密钥与条目内 TOTP 密钥隔离**：两者都用 `otpauth`，但存储键、展示界面、日志前缀必须区分；代码评审时重点查这一项。
3. **不要为“方便”留后门**：调试用的跳过令牌、万能恢复码、明文导出开关一律不得进发布分支；如开发期需要，必须用编译期开关且发布前删除。
4. **旧用户不兼容**：这是需求 v3 的直接后果，发布文案必须提前写清“全新创建、无旧数据迁移”，避免用户误以为换新版后旧数据会自动出现或可一键迁移。
5. **扩展已锁定保留**：只做 T40，不做 T41；主线（M0–M3）不依赖扩展结论，但扩展不再是待定项。
6. **请求层清理依赖认证迁移**：T12/T13 阶段 1 只完成数据 API 拆线与清理范围确认；待 T22–T23 认证重构、T30 设置去账号化后执行 T35，避免提前删除仍被旧登录流程引用的 axios / SRP 与 API。

*下一步建议：先做 T01–T04 + T10–T14（完成本地数据层与健壮性）；T12/T13 的请求层和依赖最终清理在 T22–T23、T30 完成后执行 T35。*
