# BearPassword 桌面端 UI 改版方案

## 设计目标

将桌面端密码库从“功能控件集合”整理为清晰、安静、可信赖的日常工作区。减少玻璃质感、强烈主题色和层层卡片，优先让用户快速找到条目、识别安全状态并完成复制或编辑。

## 原型范围

覆盖当前桌面端主要页面、独立窗口和关键交互状态：概览、密码库、收藏、最近访问、设置分区、初始化、首次使用、解锁、恢复、快速搜索、安全中心、新增条目、备份恢复、窄窗口，以及空态、搜索无结果、加载、错误、批量操作和删除确认。产品按本地保险库使用，不包含账户绑定或云同步界面。原型采用示例数据，不连接真实保险库。

## 页面布局重构

- **工作区外壳**：固定窄侧栏承载产品标识、主导航和本地保险库状态；设置入口位于导航区底部。页面内容区独立滚动，底部状态栏显示加密状态与全局搜索快捷键。
- **概览页**：顶部欢迎与新增操作；一行三项统计；下方左右分栏分别展示最近访问和安全状态/快捷操作。统计数字作为导航入口，不使用大面积装饰色。
- **密码库、收藏、最近访问**：标题区放页面说明、数量、导入/新增操作与搜索筛选；工作区采用列表+详情双栏。条目列表按时间分组，详情按登录信息、网站和活动记录分区。收藏和最近访问复用结构，但展示对应的分组、时间语义。
- **设置页**：独立的设置标题栏；内容区左侧使用轻量分区导航，右侧按设置组排列标签、说明与开关/选择器，安全页额外放恢复说明和固定操作区。避免把每条偏好设置包成单独卡片。
- **外观设置**：将主题设计与强调色分成两个独立设置。主题设计包含经典中性、液态玻璃、柔和层叠、高对比 4 种；强调色固定提供蓝色、青绿、绿色、紫色、珊瑚、琥珀 6 种。浅色/深色/跟随系统作为独立模式，字体和语言选项保留。界面密度与减少动效作为后续增强项。
- **认证流程**：初始化、解锁和恢复使用独立双栏版式。左侧放品牌与本地加密说明，右侧只保留当前流程表单、步骤提示和恢复/返回链接。
- **快速搜索浮窗**：单独的紧凑窗口，搜索框置顶，键盘导航提示置底，结果行直接提供复制操作，不显示完整应用侧栏。
- **安全中心**：以风险数量摘要和待处理项目列表呈现弱密码、重复密码和长期未更新密码，提供逐项查看入口。
- **新增条目**：先选择登录、信用卡、身份、安全笔记、验证器或数据库类型，再进入字段表单；登录表单含密码生成器、TOTP、自定义字段和备注入口。
- **首次使用**：按创建保险库、保存恢复密钥、添加第一条密码三步引导；明确恢复密钥的风险和保存确认。
- **备份与恢复**：展示加密备份记录、创建/导入备份和恢复密钥管理入口。
- **关键状态**：单独呈现空库、搜索无结果、解密加载、解锁错误、批量选择和删除确认，避免只设计理想路径。
- **窄窗口**：新增约 900px 宽度下的列表+详情预览，详情字段切为单列，提供返回列表操作。
- **安全提示**：使用低饱和语义色提示风险或健康状态，保持提示短小，不抢占主要工作区。

## EasyUI 视觉映射

- 背景采用近白灰（约 `#fafafa`），面板为白色；分组通过细边框、间距和灰阶区分。
- 主文字使用近黑，描述文字使用中灰；蓝色只用于选中、焦点和主操作。
- 面板圆角约 12–14px，输入和按钮高度统一；阴影仅用于弹层，不让静态面板漂浮。
- 动效只用于 hover、按下和选中反馈，建议 150–220ms，并遵循 `prefers-reduced-motion`。
- 桌面端 renderer 与扩展 popup 确定迁移至 React，以直接使用 React 组件生态。EasyUI 组件按需复制并统一到本项目 token；21st.dev 组件作为候选实现参考，逐项审查源码、依赖、许可、可访问性和行为后再接入。
- EasyUI 与 21st.dev 都不是 BearPassword 的完整产品组件库。导航、按钮、输入、选择器、菜单、提示、弹窗、标签页等通用交互优先采用 React Aria/Radix/shadcn 兼容组件；密码条目列表、详情、密码字段、密码生成器、TOTP、恢复密钥、快速搜索和本地保险库操作由项目自行实现并负责安全行为。
- Tailwind/shadcn 仅作为 renderer 的样式和通用控件基础，不把社区组件的演示配色带入产品。所有控件映射到本文件定义的中性表面、六色强调色、主题设计和明暗模式变量。

## 前端 React 迁移方案

- **迁移范围**：桌面端 `bear-password-desktop` renderer 和浏览器扩展 `bear-password-extension` popup 一并迁移到 React。Electron main、preload、IPC 通道、本地保险库与加密逻辑、扩展 manifest、background、content scripts 和扩展通信契约保持原有职责与边界。
- **目标技术栈**：React、TypeScript、Vite（桌面端继续由 electron-vite 管理 main/preload/renderer 构建）、React Router、Zustand、Tailwind CSS、Radix UI/shadcn。扩展继续使用 `@crxjs/vite-plugin`，替换 Vue 插件为 React 插件。图标统一使用 `lucide-react`；复杂表单采用 React Hook Form 与 Zod，前提是评估后确认与现有校验规则兼容。
- **保留和重用**：优先保留与框架无关的 Electron IPC 类型/契约、加密工具、数据适配、文件格式、manifest、background/content scripts、常量、国际化词条和业务规则。桌面与 popup 的 Vue 单文件组件、Pinia store、Vue composable、Element Plus 组件和依赖 Vue 响应式的代码需要逐步替换。
- **状态边界**：Zustand 只管理 UI 与应用偏好状态；敏感保险库数据仍遵循现有锁定生命周期和加密边界，不为迁移而长期缓存明文密码。Electron API 继续只通过 preload 暴露的窄接口调用，React 组件不得直接导入 Electron 模块或访问 Node API。扩展 background/content script 不挂载 React，不将 React runtime 注入网页。
- **共享逻辑边界**：共享 API、locale、theme、storage 和数据转换模块不得依赖 Vue 或 React 响应式 API；将它们整理为纯 TypeScript 函数/状态订阅接口，由桌面与 popup 各自的 React store 适配。这样 background、content script 和 popup 可继续复用纯逻辑而不捆绑 UI 框架。
- **依赖管理**：桌面端和扩展均使用 pnpm 作为唯一包管理器和锁文件来源。迁移完成后，分别移除两模块的 Vue、Vue Router（如有）、Pinia、Element Plus（桌面端）、`@vitejs/plugin-vue` 和 vue-tsc 依赖，并替换为 React、React DOM、React Vite 插件及对应类型包。
- **组件采纳规则**：EasyUI 组件适配成本低且覆盖需求时优先；21st.dev 只挑选与桌面密集工作流相符的组件，避免落地带营销式布局、重动效或不必要网络资源的实现。源码依赖不适配、可访问性不足或行为难以审查时，使用 Radix/shadcn 基础能力自行组合。
- **安全要求**：导入组件不得改变密码遮蔽、复制确认、剪贴板清理、自动锁定、键盘焦点、恢复密钥保护等既有安全行为。组件仅呈现数据和触发明确命令；敏感值的生命周期仍由业务层控制。

## React 迁移顺序与验收

1. 建立 React renderer 入口、路由、错误边界、全局 token 与主题桥接；先验证 Electron preload API 和扩展通信在新 renderer 中可调用。
2. 提取桌面端与扩展 popup 共用的纯 TypeScript 逻辑，先移除 shared locale/theme 等模块对 Vue 的响应式依赖，锁定 IPC、扩展消息和存储格式契约。
3. 迁移桌面端认证、设置、概览和密码库，再迁移扩展 popup 登录、保险库、设置及条目对话框；分别使用适合窗口/弹窗尺寸的布局，避免强行共用页面外壳。
4. 全量迁移后移除两模块的 Vue 入口与依赖，更新 Vite 插件、类型检查和 pnpm 锁文件；background/content scripts 保持独立打包，不加载 React。
5. 每阶段运行桌面端与扩展的 `pnpm run typecheck`、`pnpm run build`，并回归创建/解锁保险库、密码复制及剪贴板清理、自动锁定、托盘、快捷键、主题/语言同步、备份恢复、扩展桥接、popup 登录和网页自动填充。检查浅色/深色、四种主题设计、六种强调色、窄窗口、键盘操作和 reduced-motion。

迁移采用分阶段可构建的提交，每阶段应用都应能启动；避免 React 与 Vue 在同一 UI 页面长期并行挂载。加密、文件格式、IPC、扩展消息和用户本地配置的行为变更必须独立于 UI 框架迁移评估。

## 建议优先级

1. 建立桌面与扩展的 React 构建入口、设计 token、主题基础和 Electron preload 稳定边界。
2. 迁移认证和设置等独立页面，以及扩展 popup 的登录与设置流程，形成通用表单、对话框和导航规范。
3. 重构桌面密码库主工作区与扩展 popup 保险库，再统一概览、收藏、最近访问和快速搜索；每批页面持续验证暗色主题、键盘焦点、窗口尺寸和 reduced-motion。

## 已确定的设计方向

- 默认采用经典中性主题、蓝色强调色；浅色、深色和跟随系统独立选择。
- 密码库默认进入列表与详情双栏视图；窄窗口保留列表和详情并列布局，并提供返回列表操作。
- 首页展示安全健康摘要，安全中心承载弱密码、重复密码和长期未更新条目的处理入口。
- 产品仅使用本地保险库，不提供账户绑定或云同步入口。

## 本轮补充

- **状态原型**：空密码库、搜索无结果、条目加载、解锁失败、批量选择、删除确认。
- **新增流程**：条目类型选择，以及登录信息表单（含密码生成器、TOTP、自定义字段入口）。
- **安全与新手体验**：密码健康中心和首次使用三步引导，包含恢复密钥保存确认。
- **备份管理**：创建/导出加密备份、从文件恢复、查看或重新生成恢复密钥。
- **窗口适配**：900px 窄窗口下列表和详情并排，详情字段切换为单列。
- **外观方案**：这是现有外观设置的布局与主题模型重构。把原先以整套配色命名的预设拆分为“主题设计”和“强调色”，避免颜色选择同时改变背景、材质和组件层级。模式（跟随系统/浅色/深色）独立于这两个维度；保留现有字体与语言选项。
- **主题设计**：提供经典中性、液态玻璃、柔和层叠和高对比 4 种界面材质/层级方案。主题设计决定背景表面、组件边界、圆角和阴影方式，不决定强调色。
- **强调色**：仅提供蓝色 `#4f77d1`、青绿 `#268c8a`、绿色 `#47845a`、紫色 `#7865b1`、珊瑚 `#d16c65`、琥珀 `#b47a2b` 六种。颜色只应用于选中态、键盘焦点、进度和主要操作；正文与状态语义色维持各自的对比度和含义。
- **液态玻璃主题**：作为 4 种主题设计之一。玻璃效果用于侧栏、工具栏、浮层和少量交互控件，采用半透明底色、背景模糊/饱和度、细描边与内侧高光；密码、用户名等高敏感内容继续使用实底表面。支持 `backdrop-filter` 时使用动态玻璃材质；不支持或系统减少透明效果时退化为高不透明主题表面。避免将玻璃叠加到所有卡片。
- **原型导航**：场景导航固定在页面顶部；场景条可横向滚动并提供左右滚动按钮，当前场景自动进入可视区域。场景选择下拉和前后切换按钮可直接访问全部场景，窄视口下不再依赖手势滚动。
- **预览图**：以上各场景均已在 `docs/prototypes/all-pages/` 生成对应 PNG。

## 主题与颜色方案

- **主题入口**：主题设计与强调色分组展示，分别选择。默认主题设计为经典中性，默认强调色为蓝色；浅色/深色/跟随系统单独控制，不因切换强调色而改变表面材质。
- **主题设计选项**：经典中性、液态玻璃、柔和层叠、高对比。
- **强调色选项**：蓝色、青绿、绿色、紫色、珊瑚、琥珀，共六种。
- **材质范围**：优先用于侧栏、标题/工具栏、菜单、浮层和少量交互按钮。列表正文、密码字段和设置表单使用高不透明表面，避免背景折射影响敏感信息阅读。
- **视觉参数**：以主题背景作为玻璃背板，使用约 14–18px 背景模糊、适度饱和度、半透明语义表面、细边缘描线和轻微内侧高光。边缘高光只表达材质，不使用持续发光或大面积渐变装饰。
- **交互反馈**：仅交互控件在 hover/pressed 时显示轻微亮度或位移反馈；选中态仍以清晰边框、图标和文字标示。支持 `prefers-reduced-motion`，关闭非必要变形动画。
- **可访问性与兼容性**：遵循 `prefers-reduced-transparency` 时移除模糊并提高表面不透明度；浏览器不支持 `backdrop-filter` 时回退到静态高不透明主题表面。检查浅色、深色下的文字对比和键盘焦点。
- **性能边界**：仅对少数相邻导航/工具区域启用模糊，避免大面积多层嵌套玻璃影响 Electron 渲染性能。React/Electron renderer 采用 CSS `backdrop-filter` 与语义主题变量；iOS 原生 Liquid Glass API 不适用于当前技术栈。
- **原型位置**：在“设置 · 外观”页分别选择主题设计和强调色，右侧预览显示组合效果；四种设计与六种强调色均可独立切换。

## 旧主题配置迁移

- **新配置字段**：将原有 `theme` 拆为 `appearanceMode`（`system`/`light`/`dark`）、`themeDesign`（`classic`/`liquid`/`soft`/`contrast`）和 `accentColor`（六个固定颜色 ID）。新安装默认 `system`、`classic`、`blue`；字体和语言沿用原配置。
- **一次性迁移**：启动时读取旧 `theme` 值，按旧主题恢复明暗模式和最接近的强调色，主题设计迁移为 `classic`。写入新字段成功后标记迁移版本；旧值无效或缺失时采用新默认值。迁移不覆盖用户已有的新字段，重复启动保持幂等。
- **映射建议**：`light`、`dark`、`system` 分别迁移为对应明暗模式；旧预设 `dark`、`midnight`、`noir` 保留深色模式，其余旧彩色预设迁移为浅色模式。`ocean`/`lagoon`/`midnight` 映射青绿或蓝色，`warm`/`earth`/`noir` 映射琥珀，`bloom`/`rose` 映射珊瑚或紫色，`mint`/`forest` 映射绿色，`violet` 映射紫色；`light`、`dark`、`system` 使用默认蓝色强调色。
- **旧托盘菜单兼容**：托盘菜单当前同步旧主题 ID，改版时需将其改为同步并操作三项新偏好，或先保留旧命令并在渲染进程入口统一映射。主进程收到旧 ID 时不能丢失主题模式；主进程原生菜单颜色由操作系统控制，不尝试用强调色染色。
- **验证重点**：覆盖首次启动、旧偏好迁移、已写入新字段的升级、系统主题跟随、托盘切换以及无托盘环境。确认主题和强调色分别持久化，迁移失败时仍可用旧配置启动。
